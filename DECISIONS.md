# Decisions (product track)

Decisions taken without asking, per the brief. Newest last.

## D1. Routes: paths, with the old links kept (Phase 1)
`/` landing, `/explore` explorer, `/gallery`, `/honesty`. `?report=<id>`
anywhere is still the report; a bare `/?bbox=` or `/?job=` still opens the
explorer, so every permanent link already shared keeps working
(`web/src/lib/route.js`, tested). Each page is its own lazy chunk; the public
pages never load MapLibre. Static hosting needs an SPA rewrite to
`index.html` (in the Phase 5 hosting config).

## D2. Landing picture is an illustration, not data (Phase 1)
No invented metrics: the hero picture is a monochrome diagram of a drawn box
cut into 100 m cells with some cells hatched "not measured", captioned
"Illustration". A real result was considered and rejected: the stored
results on this machine are of Kibera and Mumbai, and putting a dense
neighbourhood on the front page as decoration fits badly with the ethics
rules. All counts on the landing page ("five of eleven flood types are
built...") are read from the generated honesty data.

## D3. Added one type token, `hero` (46/50) (Phase 1)
The token scale stopped at `display` (30 px), too small for a landing
headline. Added `type.hero` in `tokens.js` (the one source); it falls back
to `display` at 720 px and below. Nothing else in the token file changed.

## D4. Gallery = the stored run record, as stored (Phase 2)
Cards are generated by `python -m product.site_data` from
`product/gallery_cities.json` (one entry per city) and the run record each
entry names (`experiments/analysis_runs/result_2026-10-28.json`); bboxes from
`analysis/live_runs.CITIES`. Values and labels are the ones stored with the
result, shown with the date and version, because a stored result is
immutable. Consequence, stated on the page: these 28 Oct results predate
flood round 2, so e.g. river (fluvial) shows `failed` there while the
current label is `validated` in scope; the gallery links to the honesty page
for current labels.
**The three result IDs are not in any local store** (`data/results` holds
only later Kibera/Mumbai/Karnataka runs; searched the disk). "Open the
report" therefore shows the report page's "could not be loaded" message
until the three cities are re-run on the serving machine (new IDs; update
the run record or point the entry at the new one). DEPLOY.md step covers
this.

## D5. Honesty page generated from the contract, with a cross-check (Phase 3)
`product/site_data.py` reads FLOOD_TAXONOMY, flood_verdicts() (pinned,
hash-checked round files), VALIDATED_CONFIGS scope, UNBUILT_FLOOD_TYPES, the
fraction producer's labels, observability's CAUSE_LABEL, the vector track's
default label, and the constants behind the known limits (evaluation cell,
MIN_VALID_OBS, MIN_UNIT_COVERAGE, OSM regimes). The round whose evidence is
shown is picked by the contract's own rule and then checked against
flood_verdicts(); disagreement aborts generation. `tests/test_site_data.py`
fails when committed JSON != fresh build; `tests/test_web_site.mjs` fails if
the page sources type a decimal or a percentage. The page says "tested on
30 m cells, from terrain at that resolution or coarser" rather than "30 m
terrain": MERIT Hydro (fluvial's HAND) is coarser than 30 m.

## D7. Downloads built in the browser from existing public endpoints (Phase 4)
No api.py change: the report's download bar pages through
`GET /api/results/<id>/wards/<unit_type>` (already public, contract-shaped
per unit, geometry included) and builds GeoJSON and CSV client-side
(`web/src/lib/download.js`). Offered unit types: `grid` (100 m) and
`ward:*` only; `footprint` and `path` (per building / per street segment)
are never offered, and no raster is. CSV is long (one row per unit and
output) so every row carries value, status, validation label, scope note,
coverage, sources, result id, model version and code commit; `#` header
lines carry provenance and licence notes. GeoJSON flattens each output to
`<path>`, `_status`, `_validation`, `_coverage`, `_sources` (`_tier`), with
provenance under a top-level `geowatch` member. CSV cells starting with
= + - @ are prefixed with `'` (spreadsheet formula injection).
Verified end to end against stored result r476733d6905c91519bd75b6b (850
grid units) through the local API and Chrome.

## D8. Licence notes are a summary, and say so
The notes in each download summarise each source's terms as of November
2026 (Open Buildings CC BY 4.0 / ODbL; OSM ODbL; MERIT Hydro CC BY-NC 4.0
or ODbL; FABDEM CC BY-NC-SA 4.0; Copernicus DEM / Sentinel attribution;
CHIRPS, IMERG). An unmatched source is named as "licence not recorded".
GeoWatch's own licence is not chosen; the file says so. **For Kanveer:**
FABDEM and MERIT Hydro are non-commercial, so flood outputs inherit that;
it matters for funders' and insurers' use (DEPLOY.md lists it).

## D9. Building-level units must be closed on the public API (see Phase 5)
`GET /api/results/<id>/wards/footprint|path` and `.../features/footprint|path`
are public reads today (api.py's results exemption). The explorer never
requests them. The deployment wrapper (Phase 5) requires the API key for
them, so the public deployment cannot leak per-building values, without
editing api.py.

## D10. Hosting target: Render (Phase 5)
Render over Railway because: (1) **Secret Files**: the Earth Engine key is
mounted as a file (`/etc/secrets/ee-key.json`), never an env var or image
layer; Railway has env vars only, so the JSON would have to be pasted or
base64'd into one. (2) A **static-site** product with rewrite rules: the
site and `/api` share one origin (no CORS, one domain, free CDN and
auto-TLS); on Railway the frontend would be another container. (3) A
reviewable **Blueprint** (`render.yaml`) in the repo. (4) Health-check
restarts and persistent disks on Docker services. Costs: DEPLOY.md §11.
Against it: a Render disk attaches to one service, so the SFINCS worker
needs a shared queue/store first (DEPLOY.md §9); Railway has the same
limitation with volumes.

## D11. No api.py edit: a gateway in front of it (Phase 5)
`deploy/asgi.py` wraps `api.app` (uvicorn `deploy.asgi:app`, 1 process):
`/health`, CORS from env, per-client sliding-window rate limits, a global
daily cap on public analyses, JSON access logs with a salted client hash.
**The brief said rate limits are "already in the API": they are not**: only
the job pool (2 concurrent runs) and the 100 km² area cap exist. Hence the
limiter here.

## D12. Public explorer without a key in the browser (Phase 5)
Product rule: public explorer, no login. api.py protects `GET /`,
`/api/boundaries`, `/api/jobs`, `/api/imagery` with the key, and a key
inlined into the bundle (VITE_*) would be public anyway. The gateway
forwards exactly those routes with the server's key added, rate-limited
(analysis: 4/hour/client, 100/day overall; imagery 60/hour; polls 120/min;
reads 240/min; all env-configurable), and `GEOWATCH_PUBLIC_JOBS=0` turns
public analysis off. Every other protected route still needs a real key.
Per-building/per-street units are key-only (D9).

## D13. Earth Engine auth and geemap at process start (Phase 5)
Unscoped application-default credentials from a service-account key fail
Earth Engine's refresh, so `deploy/runtime.py` wraps `ee.Initialize` to use
`ee.ServiceAccountCredentials` from `GEE_SERVICE_ACCOUNT_KEY_FILE`.
`ingestion/gee_client.py` imports `geemap` at top level for a dev map helper;
the image omits geemap (Jupyter stack) and the runtime installs a stub with
`Map`. No pipeline file changed, so no result's version_id changes.
Verified: with torch / torchgeo / segment-anything / geemap / openpyxl /
pycountry blocked, 142 API/pipeline/deploy tests pass.

## D14. version_id in a container (Phase 5)
Without git, `contract.code_commit()` reads `GEOWATCH_CODE_COMMIT` and
would otherwise say "unknown" for every build, letting different code share
cache keys. The image takes it as a build arg (`deploy/code_commit.sh`, the
contract's own rule, refuses a dirty tree); production refuses to start
without it, falling back to `RENDER_GIT_COMMIT` (HEAD: more misses, never a
stale hit).
